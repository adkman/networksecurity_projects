Report for dnspoison tool:

To run the program, in the dnspoison folder,
<prompt>$ sudo go run dnspoison.go [-i interface] [-f hostnames_file] [bpf_filter_expression]

-i interface		Selects the network device to listen on. (Selects the default device, if not provided)
-f hostnames_file	File containing list of IP address and hostname pairs specifying hostnames to be hijacked
			(Poisons all the hostnames with the selected interface's IP adress, if not provided)
bpf_filter_expression	Optional BPF filter to narrow down the attack. (Default value is "udp port 53 and not src <host ip address>")

hostnames_file must be of the format:
10.6.6.6	foo.example.com
192.168.66.6	www.cs.stonybrook.edu
192.168.66.6 *.tcpdump.org

Strategy:
First, checks whether interface is provided or not. If not, selects the first available interface.
Then checks whether the hostnames file is provided or not. Reads and maintains a mapping of
hostname -> ip address in a map. If not provided, adds a single entry in the map ( * -> <interface's ip address>).
Starts listening on the interface promiscuously.
For each packet,
    Decode the DNS layer
    Check if its a DNS query,
    Check whether the queried hostname in the question matches any entry key in the map.
    If yes, then decode the Ethernet, IPv4, UDP layers
    And create a spoofed response packet and send it on the handle.
    Then log the packet for which we spoofed the response.
To create the spoofed response packet, created the layers Ethernet, Ipv4, UDP and DNS.
Filled the values in all the headers appropriately (Also referred the dnsspoof's response packet's header for the values)
Added the ip from the hostnames file map as an answer in the DNS layer.

Report for dnsdetect tool:

To run the program, in the dnsdetect folder,
<prompt>$ sudo go run dnsdetect.go [-r trace_pcap_file] [-i interface] [bpf_filter_expression]

-r tracefile	        Read packets from a (tcpdump format) tracefile. Gets precedence over the interface if provided.
-i interface		Selects the network device to listen on. (Selects the default device, if not provided)
bpf_filter_expression	Optional BPF filter to narrow down the scope of detection. (Default value is "udp port 53")

Strategy to detect dns poisoning attempt:
The packets are tracked in a map of (key string -> dnsAttackTrackingInfo struct)
where key is the combination of certain data from the packets: queriedHostname_TxID_clientIP_dnsServerIP_clientPort
and dnsAttackTrackingInfo stores two things, the count of query packets and the list of packet data corresponding to that key.
The key combination helps us to distinguish cases like same txid across different hostnames and different client ips.
The dnsAttackTrackingInfo struct helps us to avoid false positives in such rare cases like multiple dns queries from the same
client having same txID and the responses being different due to load balancing.
Now, for each packet,
    decode the IP, UDP and DNS layers
    check whether its a query or response
    For query packet,
        if there is no entry in the tracker map, then create a new one with queryCount as 1 and adding this packet to the list.
        If there is a previous entry, first, remove all the packets which we don't want to track anymore.
        (Currently assumed that we only want to track packets in a 5 second window)
        Now, add this query in the list incrementing the count appropriately.
    For response packet,
        Firstly remove all the packets which we don't want to track anymore.
        Now check whether the number of query packets is greater than the number of response packets in the list in tracker map.
        If greater, then just add the response packet in the list (As this can be a legit response packet, as there are more 
        queries in the tracker waiting for the response than already arrived responses).
        If not, then this might be a spoofed packet (or the earlier packet might be a spoofed packet).
        To identify, check the answer content of the both the response packets.
        If same, then this is a false positive (as in a rare scenario, a buggy server could resend the same packet).
        If different, then we can be certain that there was a poisoning attempt through this packet or the earlier packet
        (depending upon who won the race).
